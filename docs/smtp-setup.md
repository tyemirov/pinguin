# SMTP setup

SMTP submission and forwarding are independent optional listeners.
Both use tenant-owned domains and identities.
Their listener settings and upstream relay profiles remain shared service configuration.
The [configuration guide](configuration.md) describes environment expansion and private inputs.

A sender domain and an identity email address are globally unique.
An identity requires at least one valid forwarding recipient, including an identity used for Send-As.
SMTP credentials authenticate one exact address.
SMTP identity passwords are encrypted at rest and can be retrieved again by the authenticated owner.

The hostnames below are the tracked production declarations.
Their activation remains subject to the [deployment prerequisites](deployment.md).
Local Compose uses the ports in the [getting-started guide](getting-started.md).

## Authenticated SMTP submission for Gmail Send-As

Pingwin can expose a Gmail-compatible SMTP submission endpoint for outbound “send as” operations. A separate SMTP forwarding listener handles inbound fanout. Pingwin does not host mailboxes.

Set `smtpSubmission` in `configs/config.pingwin.yml` for the selected environment.
The configuration below describes gateway TLS termination, rather than standalone local TLS:

```yaml
smtpSubmission:
  enabled: true
  hostname: pingwin-api.mprlab.com
  listenAddr: :587
  tlsListenAddr:
  tlsCertPath:
  tlsKeyPath:
  publicPort: 465
  publicSecurityMode: ssl
  deliveryMode: direct
  maxMessageBytes: 26214400
  maxRecipients: 100
  allowInsecureAuth: true
```

Sender domains are not configured in YAML. An authenticated owner selects a tenant and adds a sender domain. The owner publishes the displayed DNS records and clicks **Check DNS**. Pingwin creates SMTP identities only under a verified tenant domain. 

In `deliveryMode: direct`, Pingwin accepts the authenticated submission. It sends the raw message to recipient MX hosts with the authenticated envelope sender.
Direct mode permits only one recipient domain per message. Pingwin does not provide DKIM signing, bounce processing, or mailbox hosting.

The gateway accepts public SMTPS on `pingwin-api.mprlab.com:465`. Caddy terminates TLS and sends the decrypted session to private port `587`. As a result, the production config leaves the Pingwin TLS fields empty and sets `allowInsecureAuth: true`. Publish only the gateway TLS listener.

The public SMTPS listener uses Caddy Layer 4 and does not use the shared HTTP request limit. Pingwin applies SMTP controls in the submission server. `server.operationTimeoutSec` controls idle command and data deadlines. 

Session limits apply globally and to each backend-visible remote host. Authentication failure limits apply to each credential username. Message limits apply to each SMTP identity. Defaults permit 200 global sessions and 20 sessions for each remote host. Defaults also permit five authentication failures per 10 minutes and 60 accepted messages per identity per hour.

For upstream delivery, set `deliveryMode: upstream` and provide:

```yaml
  relay:
    host: smtp.upstream.example.com
    port: 587
    username: upstream-user
    password: upstream-password
```

SMTP relay workflow:

1. Sign in to Pingwin.
2. Open **SMTP relay**.
3. Add the sender domain, for example `acme.example`.
4. Publish the DNS records shown by Pingwin:
   - TXT `_pingwin-challenge.acme.example` with the displayed verification token.
   - Add the displayed `a:<smtp-host>` mechanism to the `acme.example` SPF record before its final `all` directive.
   - TXT `_dmarc.acme.example` with a DMARC policy such as `v=DMARC1; p=none`.
5. Click **Check DNS**. Pingwin enables SMTP identity creation when the domain status becomes **Verified**.
6. Create an identity such as `alice@acme.example`.
7. Use the settings in the Gmail SMTP settings dialog. Open **View password** to see the settings again.
   - SMTP server: `pingwin-api.mprlab.com`
   - Port: `465`
   - Security: SSL
   - Username/password: values generated by Pingwin
8. Use **Rotate credentials** in that modal when Gmail needs a new SMTP username and password.

Pingwin validates that the SMTP login, envelope sender, and RFC 5322 `From` header all match the exact identity before accepting a message for delivery.

## Inbound SMTP forwarding for shared addresses

Pingwin can expose a separate unauthenticated SMTP listener for shared-address fanout. This listener is not a mailbox. Pingwin accepts only active identities that have forwarding recipients. It immediately forwards to each `forward_to` recipient through `smtpForwarding.relay`.
Pingwin stores no message body.

For parsed messages, the relay rewrites the sender headers to the shared identity and preserves the body.
Forwarded copies use the shared address as the outbound envelope sender.
The [delivery guide](smtp_delivery_plan.md#inbound-forwarding) defines reply metadata and behavior when header rewriting fails.

Set the `smtpForwarding` section in `configs/config.pingwin.yml`:

```yaml
smtpForwarding:
  enabled: true
  hostname: mx.pingwin.mprlab.com
  listenAddr: :25
  maxMessageBytes: 26214400
  maxRecipients: 100
  relay:
    host: smtp-relay.example.com
    port: 587
    username: relay-user
    password: relay-password
```

Because forwarding routes are stored as SMTP identities, shared-address domains use the same verified sender-domain gate as outbound SMTP relay identities.

Shared addresses are dynamic data, not YAML routes. Create or edit them from the SMTP relay page or the authenticated API:

```json
{
  "email_address": "support@help.example.com",
  "forward_to": ["alice@example.com", "maria@example.com"]
}
```

Pingwin rejects identity creation or forwarding updates unless `forward_to` contains at least one valid email address.

The inbound listener accepts `MAIL FROM:<>` null reverse-path messages so DSNs and other auto-generated loop-safe mail can be forwarded to configured shared addresses.

Use a dedicated mail subdomain for customer DNS when possible:

```dns
help.example.com. MX 10 mx.pingwin.mprlab.com.
_dmarc.help.example.com. TXT "v=DMARC1; p=none; rua=mailto:dmarc@example.com"
```

MX records apply to an entire domain, not one address. If `example.com` points to Pingwin, configure each accepted `@example.com` address. For the first release, use an address such as `support@help.example.com`. Keep the current apex-domain MX records.

Forwarded copies use the shared address as the outbound envelope sender. SPF must authorize the relay in `smtpForwarding.relay`. Use the relay provider's documented SPF include or a Pingwin-provided `ip4:` or `ip6:` mechanism.

Domain setup verification:

1. Verify DNS:
   ```sh
   dig +short MX help.example.com
   dig +short TXT _dmarc.help.example.com
   ```
	   The MX answer must include `mx.pingwin.mprlab.com`.
	   If the customer publishes SPF for forwarded copies, also verify `dig +short TXT help.example.com` returns the relay-authorizing SPF value.
2. For authenticated SMTP relay, click **Check DNS** on the SMTP relay page. Pingwin checks ownership, SPF, and DMARC records. Pingwin then updates the domain state.
3. Verify configuration:
   ```sh
   ./bin/pingwin-doctor configs/config.pingwin.yml --expand-env
   ```
4. Send an external SMTP test to `support@help.example.com` and confirm that each configured forwarding recipient receives a copy.

The gateway accepts public MX traffic on `mx.pingwin.mprlab.com:25`. Caddy sends the SMTP session to Pingwin's private forwarding capability.

If forwarding fails before final SMTP acceptance, Pingwin returns a temporary `451` response.
The sender's mail server can then retry. Pingwin does not provide IMAP, POP3, search, read/unread state, or retention for forwarded mail.


## Delivery boundaries

Submission and forwarding deliver synchronously before the final SMTP success response.
These paths do not use the persisted notification retry worker.
A temporary failure lets the sending mail server retry.
Partial forwarding and uncertain SMTP responses can cause duplicate copies during a retry.

Direct delivery requires outbound TCP port `25` and suitable DNS authorization.
Successful DNS verification alone does not establish inbox placement.
The [delivery guide](smtp_delivery_plan.md) describes certificate verification, opportunistic STARTTLS, and persistence behavior.
